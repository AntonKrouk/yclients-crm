# YClients CRM — рабочая справка

Надстройка над YClients: тянет клиентов и визиты, считает периодичность и прогноз
следующего визита, каждое утро формирует задачи админам на обзвон. Админ отмечает
результат звонка → лента событий клиента → «Обзор» владельца.

Владелец продукта — **Антон** (муж. род), учится по ходу дела: объяснять «что и почему»,
а не только «что поменял».

## Устройство кода

- `server.js` — все маршруты (~60 штук), отдаёт `public/`.
- `src/sync.js` — `run()` обходит филиалы по очереди: `fetchRecords` → `syncBranch` →
  `reconcileFuture` → прайс → покупки. В конце `rules.generate()`.
  **У цикла по филиалам нет try/catch**: падение на первом филиале (Басков) убивает весь
  синк, и задачи не создаются вообще ни по одному.
- `src/rules.js` — движок задач. Ключевое:
  - `DAILY_OPEN_TARGET = 10` — держим не больше 10 открытых задач **на филиал**. Если
    вчерашние не разобраны, новые не добираются.
  - Типы: `no_show` → `rebook` → `reactivation`, слоты раздаются чередованием.
  - Паузы после звонка: неявка/запись 14 дн., реактивация 60, отказ 90, «не звонить» 60.
  - `rebook` только при ≥3 визитах и ритме ≤180 дн.; `reactivation` — пропал дольше 2×
    периодичности, но не больше 180 дн., и ≥2 визитов.
  - Клиенты без `last_visit` или `avg_interval_days` кандидатами не становятся вовсе.
  - Дедуп по человеку (телефон): у кого карточки в обоих филиалах — задача только в том,
    где больше визитов.
  - **Deep Sleep** (`fillDeepSleep`, тип `deep_sleep`) — отдельная очередь для отсеянных:
    окно 90–730 дней с последнего визита, своя норма `DEEP_SLEEP_TARGET = 10` на филиал,
    пауза 180 дней, порядок по ценности (чек → визиты → свежесть). В `DAILY_OPEN_TARGET`
    не входит: `ENGINE_OWNED_T` его исключает, `ENGINE_OWNED` — нет (уборку проходит).
    Из конверсии админов исключён — в `/api/stats` своё поле `deep_sleep`.
- `src/yclients.js` — API-клиент, LIVE-режим включается при наличии partner-токена,
  филиала и (user-токена ИЛИ логина+пароля).

## Диагностика «не пришли задачи»

Смотреть строго в этом порядке:
1. `journalctl -u yclients-crm --since today` — отработал ли синк в 08:00 и не упал ли он.
2. Задачи **по статусам**, не скопом: `status='open'` и `status='snoozed'` — это разные вещи.
   Отложенные на будущее не видны на дашборде вовсе и в дневной лимит не считаются.
   Именно на этом 16.09.2026 сгорел час: посчитал `IN ('open','snoozed')` и решил, что
   у Баскова 16 открытых, тогда как открытых было ноль.
3. Сколько открытых по филиалам — если уже 10, движок и не должен добирать.
4. Есть ли вообще кандидаты: свежие `last_visit` / `avg_interval_days` по этому филиалу.

Готовый скрипт диагностики — в истории сессии 16.09.2026; суть: группировать по
`company_id` (387958 / 898298) И по `t.status`, плюс `date(t.created_at)` за последние дни.

## Выкат (всегда одинаково, без вариаций)

1. Правки → проверка локально на копии базы (боевую не трогать).
2. `git commit` **прямо в main**, сообщение транслитом латиницей.
3. `git push origin main` — сразу, не переспрашивать.
4. Антон сам заходит на сервер. Давать ему **два отдельных блока**, вход — первой строкой,
   каждый раз целиком:
   ```
   ssh -o ServerAliveInterval=30 root@prive7crm.ru
   ```
   ```
   cd /opt/yclients-crm && sudo -u crm git pull && systemctl restart yclients-crm
   ```
5. Проверка: `curl -s https://prive7crm.ru/api/health` — `version` = хеш нового коммита.

## Грабли

- **SSH у меня нет** — только пароль, `BatchMode` отказывает. Деплой и команды на сервере
  делает Антон. Ключ не заводить: `~/.ssh/config` на этой машине ломает ему обычный `ssh`.
- Команды для сервера — **без кириллицы**: Windows-консоль её калечит.
- Длинные однострочники с `(...) | crontab -` при вставке в SSH рвутся и успевают частично
  примениться. Крон править через временный файл.
- Репо приватный: для `git pull` на сервере Антон временно делает его публичным.
- Панели (Timeweb, YClients, GitHub) Антон держит залогиненными — смотреть самому через
  `mcp__claude-in-chrome__*`, а не диктовать ему команды.
