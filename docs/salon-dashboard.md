# Раздел «Салон» — дашборд владельца

Идея — из рилса bsuniversity.online «Дашборд владельца салона красоты» (27.10.2026): плитки
записей и выручки, вклад мастеров, направления, доход услуг в час, свободные окна на неделю
и клиенты под эти окна. Там это макет с выдуманными цифрами, у нас — настоящие данные YClients.

«Доход салона за час» из рилса у нас — **выручка в час**: оплаты мастеру и расхода материалов
в YClients-данных нет (в рилсе они из Финтабло), поэтому структуры цены «материалы / мастеру /
салону» в разделе нет. Появятся эти цифры — добавится и она.

Видят **только владелица и управляющая**: отдельный пароль `OWNER_PASSWORD`. Админы по общему
паролю раздел не видят, и сервер отвечает им 403 даже по прямой ссылке — прятать одну вкладку
мало, данные по выручке мастеров ушли бы любому, кто откроет адрес API.

## Этапы

1. **Сводка** (`/api/salon/summary`) — на данных, которые уже лежат в базе, плюс две новые
   колонки визита (`staff_id`, `duration_min`) и расписание мастеров для загрузки.
2. **Свободные окна** (`/api/salon/windows`) — расписание мастеров минус ВСЕ записи журнала
   (включая блокировки без клиента: «обучение», «под запись» — это ~20% записей недели),
   и под каждое окно — клиенты этого мастера, у которых подошёл срок. Кнопка «В обзвон»
   ставит ручную задачу админам.

## Что проверено на боевом API (27.10.2026, только чтение)

- `/records` отдаёт `seance_length` (секунды, длительность всей записи), `staff_id`,
  `technical_break_duration`. У ~20% будущих записей нет клиента — это блокировки времени.
- `GET /company/{cid}/staff/schedule?start_date=…&end_date=…` — расписание ВСЕХ мастеров
  филиала одним запросом: `[{staff_id, date, slots:[{from:"10:00", to:"22:00"}]}]`, только
  рабочие дни; бывает два слота в день (перерыв). Неделя по Баскову — 65 строк, 28 мастеров.
- Сверка: у мастера смена 10–22, одна запись 11:00 на 120 мин → `/timetable/seances` даёт
  144 пятиминутных сеанса, свободных 120 = 10 ч. Расписание минус записи сходится.
- `/company/{cid}/staff/` — `name, specialization, fired, hidden, is_bookable, …`. Есть
  служебный «мастер» АДМИНИСТРАТОР — отсекается по `is_bookable`.

## Доступ

- `.env`: `OWNER_PASSWORD=…` — один пароль на владелицу и управляющую. На странице входа они пишут
  логин **manager** (меняется `OWNER_LOGIN` в `.env`) и этот пароль; админы оставляют логин пустым и
  вводят общий пароль, как раньше. Без логина пароль владельца тоже пускает — по старой памяти.
  Подпись куки владельца включает `OWNER_PASSWORD`: сменили — все входы владельца гаснут.
- «Выйти» — в меню у всех: на общем компьютере управляющая входит своим логином после админа.
- Без `DASHBOARD_PASSWORD` (локально) вход открыт и все считаются владельцем.
- `GET /api/me` → `{ owner: bool, configured: bool }`. `configured=false` — пароль владельца
  не задан (раздел недоступен никому).
- Все `/api/salon/*` для не-владельца → `403 {error:"Раздел только для владельца"}`.

## Контракт API

Даты — московские дни `YYYY-MM-DD`. `branch` — как везде (`Басков` / `Мытнинская` / пусто = оба).

### `GET /api/salon/summary?from&to&branch`

По умолчанию — с 1-го числа текущего месяца по сегодня. Прошлый период — столько же дней
сразу перед `from`.

```jsonc
{
  "period": { "from": "2026-10-01", "to": "2026-10-27", "days": 27,
              "prev_from": "2026-09-04", "prev_to": "2026-09-30" },
  "tiles": {
    "records":   { "value": 642, "prev": 594 },                       // все записи периода (кроме напоминаний о ДР), любой статус
    "completed": { "value": 571, "prev": 530, "pct": 88.9 },          // закрытые визиты; pct — от records
    "lost":      { "value": 71,  "prev": 64,  "pct": 11.1, "no_show": 60, "cancelled": 11 },
    "unclosed":  { "value": 12 },                                     // прошедшие записи без отметки (kind='visit')
    "revenue":   { "value": 1757100, "prev": 1563000, "avg_check": 3077, "avg_check_prev": 2949,
                   "trips": 571, "goods": 84200 }                     // выручка услуг по закрытым; чек — на поход (клиент+день); goods — товары за период
  },
  "series": [ { "day": "2026-10-01", "records": 24, "completed": 21, "lost": 3, "revenue": 65400 } ], // каждый день периода, нули тоже
  "masters": [
    { "staff": "Анна Морозова", "branch": "Басков", "records": 74, "revenue": 473600, "share": 27.0,
      "avg_check": 6400, "repeat_pct": 68, "load_pct": 92, "work_hours": 160, "busy_hours": 147 }
  ],                                                                   // по убыванию выручки; load_pct = null, если нет расписания или длительностей
  "directions": [ { "name": "Волосы", "revenue": 771200, "records": 210, "share": 43.9 } ],
  "services": [
    { "service": "Кератин", "records": 2, "revenue": 18000, "avg_price": 9000, "avg_min": 120, "per_hour": 4500 }
  ],                                                                   // топ-15 по выручке, только записи из одной услуги; avg_min/per_hour = null без длительности
  "sources": { "yclients_synced_at": "2026-10-27T05:00:12.000Z", "schedule_updated_at": "…",
               "durations_known_pct": 97 }
}
```

Определения:
- **Записи** — `visits` за период по МСК-дню, `kind <> 'birthday'` (строки без kind тоже берём).
- **Состоялись** — `status='completed'`. **Потеряно** — `no_show` + `cancelled`
  (отмены неполные: удалённые записи ловим только в будущем окне синка — подписать в интерфейсе).
- **Не закрыты** — `status='upcoming' AND kind='visit' AND date < сейчас`.
- **Выручка** — `SUM(cost)` закрытых. **Средний чек** — выручка / число походов
  (уникальные `client_id` + МСК-день среди закрытых).
- **Мастер** — `visits.staff` + филиал (мастер в двух салонах — две строки, как в YClients).
  `repeat_pct` — доля закрытых записей мастера, где у этого клиента уже был закрытый визит у
  того же мастера раньше. `load_pct` — (минуты закрытых + неявок + незакрытых записей мастера)
  / (минуты смен по расписанию за период) × 100.
- **Направления** — из `visits.service_category` (первая категория записи) по словам:
  Волосы (стриж|уклад|окраш|тон|волос|кератин|причес|колор|блонд|уход), Ногти (маникюр|педикюр|покрыт|ногт|снятие),
  Брови и ресницы (бров|ресниц|ламин), Макияж (макияж|визаж), Косметология (космет|лиц|чистк|пилинг|уход за кож),
  Массаж и тело (массаж|тел|эндосфер|spa|спа), остальное — Прочее. Проверить на реальных категориях и поправить.

### `GET /api/salon/windows?branch&refresh=1`

Семь дней с сегодняшнего (МСК). Кэш в памяти 10 минут; `refresh=1` — мимо кэша.

```jsonc
{
  "updated_at": "2026-10-27T08:10:00.000Z",
  "days": ["2026-10-27", "…7 дней"],
  "min_gap": 60,
  "masters": [
    { "staff_id": 1171085, "company_id": 387958, "branch": "Басков", "staff": "Коновалова Ирина",
      "specialization": "стилист",
      "days": [ { "day": "2026-10-29", "work_min": 720, "free_min": 600,
                  "gaps": [ { "from": "13:00", "to": "22:00", "min": 540 } ] } ],   // по порядку days; не работает — work_min 0
      "free_min_total": 1260,
      "clients": [
        { "id": 123, "name": "…", "phone": "…", "last_visit": "…", "predicted_next": "…",
          "overdue_days": 12, "visits_count": 9, "avg_check": 8200, "in_tasks": false }
      ] }
  ],                                                                 // по убыванию free_min_total; только is_bookable с хотя бы одной сменой
  "totals": { "free_min": 9800, "gaps": 41, "clients": 37 }
}
```

Окна:
- Смены — из расписания. Занято — каждая неудалённая запись мастера в этот день
  `[datetime, datetime + seance_length + technical_break_duration]`, с клиентом или без.
  Напоминания о ДР (без услуг, цвет `9c27b0` или комментарий «др») временем не считаются.
- Сегодня всё, что раньше «сейчас + 30 мин», уже не окно.
- Окно — непрерывный свободный отрезок внутри смены от `min_gap` = 60 мин. `free_min` — сумма окон
  (обрезки меньше часа не считаем: туда никого не запишешь).

Клиенты под окна мастера (до 10 на мастера):
- `favorite_staff` клиента = мастер (сравнение без регистра, пробелы схлопнуть: в YClients бывает
  «Цопанова  Алина»), тот же филиал.
- `visits_count >= 2`, есть `avg_interval_days`, `predicted_next` от «сегодня − 30» до «сегодня + 7».
- Не берём: «не беспокоить», «ходит без оплаты», ручные списки (`MANUAL_LISTS`, как в `rules.js`),
  у кого по человеку есть будущая запись (`upcomingByPerson`), кому звонили последние 14 дней.
- `in_tasks` — уже есть открытая/отложенная задача (показываем, но кнопка неактивна).
- Порядок — сначала самые просроченные.

### `POST /api/salon/windows/task`

`{ client_id, staff, day, from, to }` → ручная задача (`source='manual'`, как `/api/tasks/manual`)
с причиной «Окно у {мастер}: {чт 29.10} {13:00–22:00}. Предложить запись.»,
`added_by` — «Управляющая». Ответ `{ ok, added | already, task_id, name }`.

## Салон и сбои YClients

- В шапке раздела — «Все · Басков · Мытнинская». Это тот же выбор, что селект филиала в меню
  (`currentBranch`): переключили в одном месте — другое показывает то же, раздел перечитывается.
- YClients бывает недоступен так, что соединение есть, а ответа нет. Поэтому сводка ждёт смены
  мастеров не дольше 8 с (дальше считает по базе, загрузка — по уже сохранённым сменам), а
  «Сегодня» и окна — не дольше 25 с на филиал (филиалы опрашиваются параллельно) и отдают ошибку.

## Запись в свободное окно (с 27.10.2026)

Управляющая уже договорилась с клиентом и ищет ему время. В раскрытом дне мастера каждое окно —
кнопка «Записать», у клиентов под окном — «Записать» рядом с «В обзвон». Открывается та же форма,
что у админов (`openBooking`), с подстановкой: салон, мастер, день окна и первое время, которое
YClients даёт внутри окна (`/api/booking/times` — реально свободное под длительность услуги).
Клиента выбирают поиском по базе (`/api/client-search`) или «Новый клиент» — имя и телефон, YClients
сам найдёт карточку по телефону или заведёт новую.

`POST /api/booking/create` с `from_salon: true` в журнал звонков и конверсию админов не пишет —
это не звонок; `new_client: {name, phone}` — запись без нашей карточки. После любой записи сервер
сбрасывает живой журнал «Салона» (`salon.invalidate`), окно закрывается сразу на всех экранах.

## «Сегодня» — день салона вживую (с 27.10.2026)

Режим по умолчанию. `GET /api/salon/today?branch&refresh=1` — из живого журнала YClients (тот же
кэш, что у окон: мастера — час, смены — 10 мин, записи — минута, вебхук сбрасывает записи сразу).

- Плитки: записей сегодня (по состояниям), пришли, не пришли, выручка закрытая и ожидаемая.
- Состояние записи: `now` — идёт по времени (отметку «пришёл» админы ставят, когда клиент сел в
  кресло, поэтому время важнее отметки), `done` — закончилась и закрыта, `late` — время прошло, не
  закрыта, `waiting` — впереди, `no_show` — отметка «не пришёл». **Выручка — по отметке «пришёл»**,
  а не по времени.
- Лента дня мастеров: смена, записи по состояниям, блокировки, линия «сейчас»; клик по записи —
  карточка клиента. Только мастера, у кого сегодня смена или записи.
- Прогноз выручки на 30 дней (`GET /api/salon/forecast`) — переехал из «Обзора»: «Обзор» видят
  админы, деньги салона им видеть незачем. Сервер в `/api/overview/live` его больше не отдаёт.

## Мгновенные обновления (с 27.10.2026)

`src/live.js`, два звена:

1. **YClients → сервер**: вебхук `POST https://prive7crm.ru/api/yc-webhook` (без входа). Содержимому
   не верим: берём только филиал и номер записи, саму запись перечитываем из YClients
   (`sync.importRecord`), удаление ставим, только если YClients ответил 404. Чужие филиалы —
   мимо, больше 600 событий в минуту — мимо. Необязательный ключ: `YC_WEBHOOK_KEY` в `.env` →
   адрес `…/api/yc-webhook?key=…`. Через 15 с после пачки событий — та же уборка задач, что у
   синка раз в 30 мин (`rules.generate({fill:false})` + `recomputeAutoBooked`).
   Первое событие за запуск пишется в лог (`[webhook] первое событие: ключи …`) — по нему видно,
   какой формат прислал YClients. Плановые синки остаются страховкой.
2. **Сервер → экраны**: `GET /api/events` (Server-Sent Events, только после входа). Толчок без
   данных: `yc` (журнал YClients), `crm` (любое POST/PUT/DELETE через CRM, кроме черновиков PATCH,
   скриптов и витрины), `tasks` (движок пересобрал задачи). Экран перечитывает своё тем же путём,
   что тихое обновление раз в 45 с (оно осталось страховкой). Пинг раз в 25 с и заголовок
   `X-Accel-Buffering: no` — чтобы nginx не копил ответ и не рвал соединение.

## Синк

- `visits.staff_id`, `visits.duration_min` (= `seance_length` / 60) — во всех путях записи визита
  (`syncBranch`, `syncUpcoming`, `importRecord`). Полный синк в 08:00 перечитывает 12 месяцев,
  поэтому история заполнится за одну ночь.
- Таблица `staff` (справочник мастеров) и `staff_days` (смены по дням) — обновляются в `sync.run`
  **в try/catch**: у цикла синка нет защиты, падение нового шага не должно убить задачи дня.
  Для сводки за прошлые периоды смены докачиваются лениво (прошлые дни не меняются — кэш навсегда).
